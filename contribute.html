Contributing

Tawn is built in the open and shaped by what people say they need. The most valuable contributions so far have not been code.

Helping without writing code

If you have used Tawn for ten minutes, you already know something the people building it do not.

Tell us where it lost you
“I stopped at the PostgreSQL step” is more useful than a bug report. Confusion is a defect; we just cannot see it from inside.
Say what you expected to happen
When something behaves oddly, the gap between what you assumed and what it did is the actual problem. Describe both.
Tell us what is missing
Features get built in the order people ask for them. Nothing on the roadmap is fixed.
Improve the words
Documentation lives in the repository as ordinary markdown. A pull request fixing a sentence that misled you is a real contribution, and the easiest kind to make.

The feedback form reaches us directly. So does opening an issue, or email at testimonyadekoya.02@gmail.com.

Setting up to develop

You need Python 3.12, PostgreSQL with pgvector, and Node 20 if you are touching the interface.

terminal
$ git clone https://github.com/tawn-hq/tawn.git
$ cd tawn

$ python3 -m venv .venv
$ .venv/bin/pip install -e ".[full,dev]"
$ .venv/bin/tawn db setup

# enables the commit-message check
$ git config core.hooksPath .githooks

Then confirm it works:

terminal
$ .venv/bin/python -m pytest -q
# expect 1,171 passed, about four minutes

If a large block fails at once, PostgreSQL is usually unreachable rather than your change being wrong.

The interface

terminal
$ cd frontend && npm install
$ npm run dev        # proxies /api to :8787

Run tawn web start in another terminal so there is an API to proxy to. After a production build you must copy the output into the package, or an installed copy serves a stale interface while your dev server looks correct:

terminal
$ npm run build
$ rm -rf ../src/tawn/web/dist && cp -r dist ../src/tawn/web/dist

The rules that apply

Grant-check every path
Anything reading or writing outside ~/.tawn goes through path_allowed() first, and any tool needing network or shell access checks capability_allowed(). Skipping that is the one defect that gets a change rejected outright — it is the gate the whole design rests on.
Never expose the web API
It binds to localhost and has no authentication. Anything that tunnels or rebinds it is a security defect until sign-in ships.
Prices come from vendor documentation
Never from memory. A missing price is reported honestly as unpriced; a wrong one corrupts the spend figures with no signal that anything is off.
Test first
A failing test, then the smallest change that makes it pass. Tests must never touch your real ~/.tawn — use the tawn_home fixture.
Conventional commits
feat(scope): imperative subject, lowercase, no trailing period. The hook rejects anything else. Explain why in the body, not what.
Secrets stay in the keyring
Never in code, never in committed config, never in a model's context. Configuration may hold the names of environment variables, never their values.

Things that will bite you

Alembic autogenerate does not work here
The config points at an in-memory database, so autogenerate cannot see the real schema — and when it runs it emits a reference with no import. Write migrations by hand.
A running server holds old code
After changing anything the background process touches: tawn web stop && tawn web start. tawn doctor warns when the running copy is older than the files on disk.
The vector column has no fixed width, on purpose
Pinning it to one model's size meant every model switch broke indexing. Different widths coexist, which is why changing model still requires re-indexing.
Silent exception handlers are load-bearing — and overused
The background loop runs several jobs that are each best-effort, so one failing must not stop the others. There are also 26 of them, which is too many. Do not add one without a comment saying why.

Where to start

  1. The decision log — docs/ROADMAP.md, newest first. The fastest way to understand why the code looks the way it does, including the mistakes.
  2. The permission model — src/tawn/capability/grants.py, about 150 lines.
  3. What the model can reach — src/tawn/model/tools.py.
  4. The pipeline — src/tawn/compiler/compiler.py, which everything else feeds.

Full development notes live in INSTALL.md and the rules in CONTRIBUTING.md.

No contribution is too small. A typo fix, a sentence that reads better, a note saying the install guide assumed something you did not know — all of it counts.
